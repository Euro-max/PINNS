# PINC-MPC for vehicle control

This repository trains a physics-informed neural network for control (PINC, after Antonelo et al., arXiv 2104.02556) and uses it as the prediction model of a model predictive controller (MPC) for a car. The network maps the time since the last control update, the current state and the input to the future state. It is compared with the same network trained on data only, with MPC using the exact model, and with a linearised MPC. Every number and figure in the paper comes from a script in this repository and is listed in `results/MANIFEST.md`.

The original code (kept unchanged in `legacy/`) had defects that made its results invalid, the most serious being that the closed loop never simulated the vehicle. `docs/DEFECTS.md` lists all twenty and where each one is fixed. `docs/STATUS.md` gives the current state of the work, and `TASKS.md` is the specification the rebuild followed.

## Two studies

Study 1 uses a single-track (bicycle) vehicle model, and the physics term in the loss is that same model. The physics term cut the error of the learned dynamics 13-fold and the 50-step prediction error about 2-fold over five seeds, and the test error 14-fold with only 100 training trajectories. In closed loop, PINC-MPC tracked as well as MPC with the exact model.

Study 2 (`docs/PLAN_HIGH_FIDELITY.md`) makes the vehicle more realistic while the physics term keeps the simplified model. The vehicle is a four-wheel model with Magic Formula tyres (a 205/60R15 tyre from the MathWorks Vehicle Dynamics Blockset), load transfer, wheel speeds and actuator lag. Variant M0 is calibrated so the simplified physics is right in gentle driving, and M1 also has its tyre stiffness and actuator lags wrong. Over five seeds, with 100 training trajectories the simplified physics lowered the one-step error 3-fold and the 10-step error 6-fold on M0. With 1000 or 20 000 trajectories it gave no reliable gain, and on M1 the physics term made the network worse unless it could learn the physics parameters. A grey-box model, where the network learns a correction to the simplified physics' own prediction, was more accurate than PINC at every data size and never lost the car in closed loop. PINC-MPC remains 4 to 6 times faster than grey-box MPC with a non-stiff version of the physics, which meets the 0.1 s real-time budget up to a horizon of 20 steps where PINC meets it up to 40.

## Layout

```
pinc/          library: config, vehicle models (single-track, high-fidelity, tyres), prior, data, model,
               loss, training, MPC, references, closed-loop simulator, metrics, job scheduler
experiments/   e1 to e25 (listed below)
tests/         pytest suite
configs/       default.yaml (Study 1), hf_m0.yaml and hf_m1.yaml (Study 2, generated by scripts/make_hf_configs.py)
scripts/       scale and config generation, run queues, MATLAB export of the tyre data
results/       generated only; every run folder has config.json, meta.json (seed, git hash, versions) and summary.json
docs/          status, defects, vehicle model, architecture trials, results, plan for Study 2
legacy/        the original files, imported by nothing
```

The paper source (`LATEX/`) and the scripts that build its tables and the poster are kept outside git.

## Install

The code runs on Python 3.13 with TensorFlow 2.21.0, the latest stable release. Pinned versions are in `requirements.txt`.

```
python3.13 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

If the system Python has no `venv` or `pip` module (for example WSL without `python3-venv`), use [uv](https://docs.astral.sh/uv/) instead, and add TensorFlow's CUDA extra for an NVIDIA GPU:

```
uv venv --python 3.13 .venv
uv pip install --python .venv/bin/python -r requirements.txt "tensorflow[and-cuda]==2.21.0"
```

`pinc/__init__.py` handles two GPU problems found on WSL2. It lets TensorFlow allocate GPU memory as needed, because reserving the whole GPU up front fails, and it preloads the cuSOLVER library, which TensorFlow 2.21 otherwise does not find, so it silently runs without the GPU. Training must stay in float64, because in float32 the L-BFGS stage stops after a few iterations and the model ends up about 5 times worse (`results/env_check/`).

Study 2 needs the tyre data, which is MathWorks data and not stored in the repository. Run `scripts/export_tyre_params.m` and `scripts/export_tyre_reference.m` in MATLAB with the Vehicle Dynamics Blockset and copy the output into `data/tyre/`. Without it the Study 2 tests are skipped.

## Test

```
.venv/bin/python -m pytest -q
```

The most important tests are in `tests/test_sim.py`. A controller that always returns zero input, and a prediction model that returns constant garbage, must both produce a large tracking error, and a second test searches the code for any line that sets the vehicle state from the reference. The Study 2 tests check the tyre model against MathWorks' own solver, the high-fidelity vehicle against the single-track model in gentle driving, and the prior against a separately written reduced vehicle.

## Train

```
.venv/bin/python -m pinc.train --config configs/default.yaml --seed 0 --run-id pinc_default_s0
.venv/bin/python -m pinc.train --config configs/hf_m0.yaml --seed 0 --run-id my_hf_run --set loss.lam=0.01
```

Any config entry can be changed with `--set a.b=value`. Training runs Adam and then L-BFGS, resamples the collocation points every epoch, and keeps the checkpoint with the best validation loss. The output goes to `results/models/<run-id>/`.

## Experiments

Study 1:

```
e7_architecture       network depth, width and regularisation, 56 trainings
e6_ablations          physics weight and ablations of each loss term
e1_open_loop          one-step and chained prediction accuracy

e4_timing             MPC solve time against prediction horizon
e5_robustness         plant mismatch (mass, tyre stiffness, friction, a force disturbance)
e8_vx_residual        rescaling of the speed residual, which led to the per-state output scaling
e9_physics_learning   time-derivative error and chained error per model
e10_confirm           five-seed PINC against data-only comparison
e11_convergence       training-budget check (5000 L-BFGS iterations)
e12_collocation       number of collocation points
```

Study 2:

```
e13_prior_error       how far the simplified physics is from the realistic vehicle, by driving condition
e14_hf_lambda         physics weight and wheel residuals at 20 000 trajectories
e15_hf_data           physics against data-only at 100, 1000 and 20 000 trajectories, 3 seeds
e16_hf_theta          physics parameters learned during training (M1)
e17_hf_compare        all learned models over 5 seeds, with the grey-box baseline (M0 and M1)
e18_hf_closed_loop    closed loop on the realistic vehicle: 5 manoeuvres, every controller
e19_hf_distill        a plain network trained on extra samples labelled by the grey-box model (exploratory)
e20_hf_greybox_qs     the grey-box model with a non-stiff (quasi-steady) version of the physics
e21_architectures     nine network architectures for PINC against the 8x64 MLP (one test, 3 seeds)
e22_anchored_confirm  the prior-anchored network over 5 seeds, with and without the physics loss (M0, M1)
e23_anchored_extend   the prior-anchored network in Study 1, its physics weight, and 20 000 trajectories
e24_anchor_tuning     tuning the anchor's settings
e25_prior_accuracy    the full and the quasi-steady simplified physics against the realistic vehicle
```

Run any of them with `.venv/bin/python -m experiments.<name>`. Every script accepts `--run-id`, `--seed`, `--set key=value` and `--quick` (reduced sizes), and the ones that compare controllers accept `--pinc-model` and `--blackbox-model`. Scripts that train many models accept `--slots`, which runs one training per listed device at the same time (for example `gpu,cpu` or `gpu,gpu,cpu`). `docs/RESULTS.md` and `docs/STATUS.md` give the results of each experiment.

## How the comparison is kept fair

- All controllers in an experiment run against the same simulated vehicle and the same references, and they only get the nominal vehicle parameters. Perturbed parameters and disturbances only reach the vehicle.
- The PINC and data-only networks share the network, training data, optimiser budget and seeds, and only the physics weight differs.
- The MPC uses the same cost, solver, settings and warm start for every prediction model. Solve times are measured on one CPU thread with the GPU hidden, after a warm-up solve that compiles the cost function.
- Errors are measured after each vehicle step against the reference at the new time.

## Hardware and runtimes

The Study 1 results were produced on an Intel Core Ultra 9 275HX in a virtual machine with 6 CPUs and no GPU. Later work used the same laptop with all 24 threads and its RTX 5080 Laptop GPU under WSL2. Each results folder records the CPU and package versions in `meta.json`.

| step | time |
|---|---|
| `pytest` (all tests, with tyre data) | about 20 min, mostly the high-fidelity MPC tests |
| one Study 1 model (300 Adam epochs and 500 L-BFGS) | about 4 min on the GPU, 8 min on the old 6-CPU machine |
| one Study 2 model (6000 Adam steps and 2000 L-BFGS) | about 6 to 9 min |
| E3 closed loop | about 20 min |
| E15 (36 trainings on two devices) | about 4 h |
| E18 closed loop (one variant, all controllers) | about 3 h, most of it the true-model NMPC at about 8 s per solve |

The GPU gives only a small speed-up for these networks, because they are small and computed in float64. On this laptop the CPU trains the Study 2 models faster than the GPU, so the best throughput comes from running jobs on both.

## Reproducibility

Seeds fix the data, the initialisation and the collocation points, and every run records its seed, git hash and package versions. A rerun on the same machine and software reproduces a model exactly (`results/phase1_check`). A different TensorFlow version or device changes the last digit of some calculations, and L-BFGS amplifies this: retraining the main Study 1 model with TensorFlow 2.21.0 instead of 2.22.0rc0 changed its validation loss by 4.5%, which is within the 9.6% spread between training seeds (`results/tf221_check`). The published Study 1 results were produced with TensorFlow 2.22.0rc0. Numbers should be reported with the confidence intervals the scripts produce.
